GiftWrapt is a [Model Context Protocol](https://modelcontextprotocol.io) server. Any MCP-capable assistant can connect to your deployment, sign in as you, and then add things to your lists, read the lists of people you shop for, claim gifts, keep track of what you have bought, and act on GiftWrapt's own suggestions. There is nothing extra to install or host: the server is built into the app.

<Aside type="note">
An assistant acts **as you**, with exactly the access you have and never as an admin. It sees what you see: your own lists never show who claimed what, and other people's lists do.
</Aside>

## Turn It On

An admin enables the feature once per deployment:

<Steps>

1. Open **Admin → General** and turn on **Enable MCP Server**.

2. Open **Admin → MCP**. The page shows the server URL to hand to users, checks that the two discovery documents are reachable at your origin, and lists the clients that have registered and every active connection.

</Steps>

With the switch off, nothing related to assistants exists: the endpoint, the sign-in pages, the discovery documents, the admin page, and every connected assistant stop at once.

## Connect an Assistant

Every client needs one thing: your deployment's server URL, which is your site's address followed by `/api/mcp` (for example `https://gifts.example.com/api/mcp`). You can copy it from **Settings → Connected Apps** at any time. The first time a client connects, it sends you to GiftWrapt to sign in (if you are not already) and to approve the connection.

<Tabs>
<TabItem label="Claude.ai">

In GiftWrapt, open **Settings → Connected Apps** and press **Add to Claude**. Claude opens with your deployment's name and server URL already filled in; confirm, then finish the sign-in and consent in the browser window that opens. To do it by hand instead, open **Settings → Connectors → Add custom connector** in Claude and paste the server URL. The connector then shows up in every Claude chat, on the web, in the desktop app, and on mobile.

</TabItem>
<TabItem label="Claude Code">

```bash
claude mcp add --transport http giftwrapt https://gifts.example.com/api/mcp
```

Then run `/mcp` inside Claude Code and sign in when prompted.

</TabItem>
<TabItem label="Cursor, VS Code, Windsurf">

Add the server to the client's MCP configuration as a URL entry:

```json
{
  "mcpServers": {
    "giftwrapt": { "url": "https://gifts.example.com/api/mcp" }
  }
}
```

</TabItem>
<TabItem label="ChatGPT">

In developer mode, add a connector with the server URL. ChatGPT registers itself with your deployment and walks you through the sign-in.

</TabItem>
<TabItem label="Anything else">

Clients that only run local (stdio) servers can bridge through `mcp-remote`, which handles the sign-in in your browser:

```json
{
  "mcpServers": {
    "giftwrapt": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://gifts.example.com/api/mcp"]
    }
  }
}
```

</TabItem>
</Tabs>

You are asked to approve the connection every time a client starts a fresh sign-in. Once connected, a client stays signed in for 30 days of inactivity and refreshes itself while you keep using it.

## What an Assistant Can Do

The assistant gets a set of tools that mirror the app. A few examples of what you can ask:

- "Add this to my wishlist" with a product link. The page is read for the title, price, and image, exactly like pasting a link in the app.
- "What's on Mom's list that nobody has claimed yet?" The assistant sees her list the way you would as a gifter, including what others already claimed and how many of each item remain.
- "I bought the espresso machine for Sam with Kate." The claim is recorded with Kate as a co-gifter, so both households get credit.
- "What have I spent on Christmas so far?" A summary of your claims and off-list gifts with totals per person.
- "Who has a birthday in the next month that I haven't planned a gift for?"
- "Tidy my list." Duplicates, missing prices, items that look like alternatives of each other, and GiftWrapt's own suggestions, with proposed edits before anything changes.
- "Roast my brother and make sweeping generalizations about him based on the stuff he wants." Not everything has to be productive. The assistant reads his list the way you can and takes it from there.

Three ready-made prompts come with the server (plan gifts for someone, tidy a list, what's coming up) for clients that surface prompts.

### All tools

Every tool an assistant can call, generated from the server itself. "Reads" tools only look things up; "Changes" tools add, edit, or remove something, and assistants ask before using the destructive ones. Tools for features your deployment has turned off answer that the feature is off.

| `create_dependent` | Changes | Add a dependent (a pet, a baby, anyone without their own account) that the user and any extra guardians will manage lists for. Admin only on this deployment, matching the web. |
| `create_item_group` | Changes | Group items on one of the user’s lists. An "or" group means pick one of these (once any is claimed the rest lock); an "order" group means buy them in sequence. Items in a group share the group’s priority. Optionally add items right away. |
| `create_list` | Changes | Create a list for the user (or for a dependent they manage). Gift-ideas lists are always private and may target the person the ideas are for. Holiday lists need a custom_holiday_id from this deployment. Ask before creating if the user already has a list of that type. |
| `delete_item` | Changes (destructive) | Remove an item from one of the user’s lists. If a gifter had already claimed it, the item quietly enters a pending-deletion state and the gifter is alerted; the user never sees that difference. Confirm with the user first. |
| `delete_item_group` | Changes (destructive) | Remove a group. Its items stay on the list, ungrouped. |
| `delete_list` | Changes (destructive) | Delete a list the user owns. If any item on it has already been claimed by a gifter, the list is archived instead of deleted so gift history survives; the result says which happened. Confirm with the user first. |
| `delete_off_list_gift` | Changes (destructive) | Remove one of the user’s off-list gifts. |

Only `lists[].items` are things the person asked for; `myGiftIdeas` are the user’s private notes that the person never sees, so present them separately and never as on the person’s list. Give person_id from list_people. |
| `get_list` | Reads | A list the user owns or can edit, with its items, item groups, and reveal schedule. Owner view: claims are never included, so never guess whether something was bought. A giftideas list holds the user’s private ideas for someone else, not things that person asked for. Use get_wishlist for other people’s lists. |
| `get_me` | Reads | The signed-in user: profile, partner, children and dependents they manage, their primary list, and which features this deployment has turned on. Call this first. |
| `get_wishlist` | Reads | One list belonging to another person, in the gifter view: its items with what is already claimed and how many remain, pick-one / in-order group rules, off-list gifts other gifters are bringing, and, kept separate, the user’s own private gift ideas for this person. Only `items` are things the person asked for; `myGiftIdeas` are the user’s notes that the person never sees, so never present them as on the person’s list. Give list_id, or person_id to use that person’s primary list. To plan a gift for someone across all their lists, use get_gift_context instead. Never works on the user’s own lists (use get_list). |
| `list_comments` | Reads | The conversation on an item the user can see (questions about sizes, coordination between gifters). Only available when the deployment has comments turned on. |
| `list_my_gifts` | Reads | Everything the user (or their partner) is giving: claims and off-list gifts across every list, with costs and totals per recipient. Filter by recipient_id (user or dependent) or by list type. Costs are this household’s share. |
| `list_my_lists` | Reads | Every list the user can edit: their own (wishlists, birthday, Christmas, holiday, gift-ideas), lists shared with them as an editor, and lists belonging to children or dependents they manage. Owner view: never includes claims. |
| `list_people` | Reads | Everyone whose lists the user can see and shop from: family, friends, children, and dependents (pets, babies), each with their birthday and their visible lists. Use a person’s primary list id or a list id with get_wishlist to shop. Optional query filters by name or email. |
| `list_received_gifts` | Reads | Gifts that have been revealed to the user (and to dependents they manage): what was given and by whom, newest first. Only revealed gifts appear; unrevealed claims stay hidden. |
| `list_recommendations` | Reads | GiftWrapt’s own suggestions for the user’s lists (stale items, duplicates, grouping, missing prices, set-up nudges), with the actions each one offers. Pass include_resolved to also see dismissed and applied ones. Requires the deployment’s intelligence feature. |
| `list_upcoming_occasions` | Reads | Birthdays of everyone the user can shop for (including children and dependents), plus the holidays this deployment celebrates and the user’s anniversary, within the next N days, each with whether the user has already planned a gift. Sorted soonest first. |
| `lookup_barcode` | Reads, reads the web | Identify a product from a UPC / EAN barcode number. Returns candidate titles, brands, images, and product URLs to feed into add_item. |
| `move_items` | Changes (destructive) | Move items to another list the user can edit. Moving between lists of different types (for example wishlist to gift-ideas) clears any claims gifters had made, so confirm with the user first. |
| `preview_url` | Reads, reads the web | Read a product page and return its title, price, images, and the choices a buyer must make, without adding anything. Useful before add_item or to check a price. |

| `search_my_items` | Reads | Find items across every list the user owns by words in the title or notes. Results from gift-ideas lists (isGiftIdea true) are the user’s private ideas for someone else, not things the user or that person asked for. |

| `set_item_availability` | Changes | Mark an item unavailable (sold out, discontinued) so gifters skip it, or available again. |
| `set_primary_list` | Changes | Mark one of the user’s lists as their primary list (the default for add_item and the one others see first). Gift-ideas lists cannot be primary. |
| `unclaim_item` | Changes (destructive) | Release one of the user’s claims so others can give the item. Permanent: the claim and its notes are deleted. Confirm with the user first. |
| `update_claim` | Changes | Change the quantity, cost, notes, tracking number, or co-gifters on one of the user’s claims (their partner’s too). co_gifter_ids REPLACES the whole set; pass [] to clear. The partner is already credited automatically and need not be listed. |
| `update_dependent` | Changes | Rename a dependent or set their birthday. Admin only on this deployment, matching the web. |
| `update_item` | Changes | Change an item’s title, URL, price, notes, priority, quantity, or image. Pass null to clear a nullable field. Only fields you pass change. |
| `update_item_group` | Changes | Change a group’s type, name, or priority. An "or" group means pick one of these (once any is claimed the rest lock); an "order" group means buy them in sequence. Items in a group share the group’s priority. |

### What stays private

- Your own lists never reveal claims to the assistant, so your surprises stay surprises even if you ask directly. Marking items received (which reveals the givers) is a deliberate action the assistant will ask about.
- On other people's lists, other gifters' costs and private notes stay hidden; only who is giving what is visible, as in the app.
- Restricted viewers see the same filtered view they see in the app.
- Child accounts cannot connect an assistant at all.

## Manage Connections

- **Settings → Connected Apps** lists the assistants connected to your account with when they were last used. **Disconnect** signs that assistant out immediately.
- **Admin → MCP** shows every registered client and every active connection across users. Admins can revoke a single connection, disable a client (which signs out everyone using it and blocks new sign-ins), or delete it. Clients re-register automatically the next time someone connects with them.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| The client says it cannot find the authorization server. | A reverse proxy is not forwarding paths under `/.well-known/`. The **Admin → MCP** connect card checks both discovery URLs; both must return JSON at your public origin. |
| The client gets a 503 from the server. | **Enable MCP Server** is off. |
| Claude (web, desktop, or mobile) shows "Authorization failed" right after you click Allow, while Claude Code connects fine. | A firewall in front of your deployment is blocking AI-assistant user agents. Claude's hosted connector calls your server as `Claude-User`; rules such as Vercel's **AI Bots** managed ruleset or Cloudflare's AI crawler blocking reject it at the edge, so the request never reaches GiftWrapt. Add a bypass or allow rule for the path `/api/mcp`. |
| Sign-in works but the client is told it is unauthorized afterwards. | The connection was revoked or the client was disabled by an admin. Reconnect. |
| A child account cannot connect. | By design. |
| Requests are refused with "too many requests". | Per-user limits: 120 tool calls a minute, and the same scrape and barcode limits the app uses. |
